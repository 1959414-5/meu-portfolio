01 · Visão geral

O problema de negócio que o projeto simula

Uma operação industrial reúne dados de diferentes etapas. O desafio é estruturar essas informações de forma consistente e conseguir responder perguntas práticas sem depender de consultas isoladas e difíceis de manter.

Objetivo

Construir uma base relacional de demonstração e utilizar SQL para transformar registros operacionais em análises que apoiem decisões sobre vendas, disponibilidade de materiais e desempenho da produção.

  • Definir entidades, relacionamentos e regras de integridade.
  • Gerar dados de teste coerentes com o cenário industrial.
  • Criar consultas reutilizáveis para indicadores e análises.
  • Examinar planos de execução e o efeito de índices.

Perguntas que a base permite responder

  • Qual é o faturamento, o ticket médio e a situação dos pedidos?
  • Quais materiais estão disponíveis e quais precisam de reposição?
  • A quantidade planejada para produção está sendo cumprida?
  • Como o consumo real de matéria-prima se compara ao previsto?
  • Como os índices alteram o volume de linhas examinadas nas consultas?
Escopo e confidencialidade: este é um projeto independente, feito com cadastros, pedidos, movimentações e apontamentos fictícios. Não utiliza banco de dados, documentos, logotipo ou informações comerciais reais de qualquer empresa.

04 · Análises desenvolvidas

Três frentes conectadas à operação

As consultas do projeto integrador foram agrupadas por área de negócio e executadas sobre a base fictícia.

01 / COMERCIAL

Pedidos e faturamento

Consolidação de indicadores para acompanhar o desempenho comercial.

  • Faturamento e ticket médio.
  • Pedidos entregues, pendentes e sem itens.
  • Faturamento por cliente e participação na receita.
  • Classificação e análise de prazos.
02 / ESTOQUE

Disponibilidade e reposição

Visibilidade do saldo e da necessidade de materiais para atender à produção.

  • Saldo por produto e movimentações.
  • Alertas de estoque mínimo.
  • Necessidade de matéria-prima por ordem.
  • Demanda considerando perdas previstas na estrutura.
03 / PRODUÇÃO

Produtividade e consumo

Comparação entre o que foi planejado, produzido, aprovado e consumido.

  • Quantidade planejada, produzida e aprovada.
  • Taxa de conclusão e percentual de refugo.
  • Indicadores por etapa, centro de trabalho e máquina.
  • Consumo previsto versus consumo registrado.
05 · Técnicas SQL

Recursos aplicados na prática

O foco não foi apenas escrever consultas, mas combinar técnicas de SQL para estruturar análises, tratar exceções e expressar regras de negócio.

Exemplo · CTE para demanda de materiais
WITH producao_pendente AS (
    SELECT
        op.id_ordem_producao,
        op.id_produto,
        GREATEST(
            op.quantidade_planejada
            - COALESCE(SUM(ap.quantidade_produzida), 0),
            0
        ) AS quantidade_pendente
    FROM ordens_producao op
    LEFT JOIN apontamentos_producao ap
        ON op.id_ordem_producao = ap.id_ordem_producao
    WHERE op.status_ordem NOT IN ('CONCLUIDA', 'CANCELADA')
    GROUP BY
        op.id_ordem_producao,
        op.id_produto,
        op.quantidade_planejada
    HAVING quantidade_pendente > 0
)
SELECT *
FROM producao_pendente;

Trecho ilustrativo de uma das etapas da consulta de necessidade de reposição. No repositório está disponível a consulta completa, incluindo a composição dos materiais, cálculo de perdas e comparação com o saldo do estoque.

06 · Performance

Comparação de índices em uma base de teste

Foi criado um conjunto isolado de 100.000 movimentações fictícias para observar o efeito de índices simples e compostos em uma consulta filtrada por produto, origem e data.

CenárioLinhas examinadasTempo observado
Sem índice secundário100.00041,2 ms
Índice simples1.0001,61 ms
Índice composto310,0916 ms

Índice avaliado

CREATE INDEX idx_bench_produto_origem_data
ON benchmark_movimentacoes (
    id_produto,
    origem_movimentacao,
    data_movimentacao
);

O que o plano mostrou

No cenário medido, o índice composto permitiu aproveitar os três filtros, examinar menos linhas e eliminar a operação Sort no plano observado. A escolha do índice pelo otimizador foi conferida após atualização das estatísticas.

Os tempos são medições pontuais no MySQL Server 8.4.13 com InnoDB, usando dados artificiais e ambiente local. São resultados daquele teste, não uma promessa de ganho em produção. Índices também têm custo de armazenamento e podem aumentar o trabalho de INSERT, UPDATE e DELETE; a escolha precisa considerar o padrão de leitura e escrita.

08 · Organização do repositório

Projeto documentado e reproduzível

Os arquivos foram separados por finalidade para facilitar a navegação e permitir que outra pessoa explore a modelagem, os scripts e os resultados.

Principais diretórios
